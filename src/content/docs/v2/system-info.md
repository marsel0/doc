Эта страница нужна как короткая памятка по окружениям. Она не дублирует интеграционные шаги, а помогает быстро понять, куда стучаться API-клиентом и где проверять UI.

## Тестовое окружение

Если вы смотрите эту документацию с параметром `?domain=dev.com`, именно этот домен и считается вашим тестовым или целевым инстансом.

Минимально для теста нужны:

- `BASE_URL = [[BASE_URL]]`
- merchant UI: `https://[[DOMAIN_URL]]/login`

Что важно:

- в тесте набор trade methods может быть уже, чем в production;
- callback и подпись нужно проверять сразу, а не откладывать до production;
- после таймаута create-запроса ордер нужно дочитывать, а не создавать дубль.

## Рабочее окружение

Для production используется ваш рабочий домен инстанса и те же endpoint-ы `public/api/v1`, что и в тесте.

Практически это означает:

- меняется домен;
- ключи берутся production-магазина;
- callback-обработчик должен быть уже идемпотентным и логируемым;
- логи по `externalOrderId`, внутреннему `id`, `status` и `statusDetails` должны сохраняться у вас.

## Demo-стенд

Если у команды есть отдельный demo-стенд или тестовый merchant UI, его лучше использовать только для ручной проверки сценариев:

- redirect flow;
- H2H-экранов;
- callback-доставки;
- спорных кейсов по статусам.

Demo-стенд не должен быть единственным источником проверки интеграции. Источником истины остаются реальные API-ответы и callback.

## Что проверить до production

1. Все create-запросы используют уникальный `externalOrderId`.
2. Callback проходит проверку подписи.
3. UI показывает клиенту фактический `amount`, а не только `initialAmount`.
4. После таймаута create-запроса система умеет дочитывать ордер по `externalOrderId`.
5. Спорные кейсы обрабатываются через чтение статуса, диспуты и чеки, а не вручную.
