---
title: "Типы оплаты: payment.type"
description: "Назначение кодов payment.type, ограничения PayIn и PayOut"
---

`payment.type` выбирает платёжный маршрут и формат реквизитов. От него зависят:

- какие реквизиты платформа выдаст клиенту в PayIn;
- какие реквизиты получателя магазин должен передать в PayOut;
- нужен ли банк, QR-код, ссылка, номер телефона, карты или счёта;
- какие данные плательщика понадобятся для сопоставления платежа.

## Откуда брать коды

Используйте коды, согласованные с платформой, свою таблицу кодов либо получите
их через [`GET /shop/trade-methods`](/doc/api/shop/04-dictionaries/#получение-методов)
для PayIn и
[`GET /shop/trade-methods/payout`](/doc/api/payout/04-dictionaries/#get-shoptrade-methodspayout)
для PayOut.

Общий список ниже объясняет коды, но не является списком доступных методов.
Доступность зависит от магазина, валюты, банка, лимитов и текущих маршрутов. Если
передаёте `bank`, используйте согласованную с `paymentType` пару.

## Основные типы

| `payment.type` | Для чего нужен | Типичные реквизиты | Технические ограничения |
| --- | --- | --- | --- |
| `sbp` | Перевод через СБП | Телефон, получатель, иногда ссылка | Для PayOut `phone` — от 7 до 16 символов. `customerBank` означает банк отправителя, а не получателя |
| `sberpay` | Перевод через SberPay | Телефон получателя | Используйте с согласованными банком и валютой; не заменяйте на `sbp` самостоятельно |
| `card2card` | Перевод на банковскую карту | Номер карты, владелец, иногда срок действия | В PayOut `cardInfo` — ровно 16 цифр. Если `payment.bank` не передан, банк ищется по первым 6 цифрам карты, затем используется настроенный вариант |
| `account_number` | Банковский перевод по номеру счёта | Номер счёта, получатель, BIC/ИНН при наличии | Формат счёта зависит от страны и способа оплаты; проверяйте `pattern` и `maxLength` из `fields` |
| `phone_number` | Перевод по номеру телефона вне СБП | Телефон, иногда ссылка | В PayOut `phone` — от 7 до 16 символов; необходимость банка зависит от способа оплаты |
| `sim` | Пополнение баланса SIM-карты | Телефон оператора | Это не обычный банковский перевод. Оператор и банк должны соответствовать согласованному маршруту |

## Трансграничные типы

| `payment.type` | Назначение | Отличие |
| --- | --- | --- |
| `tsbp` | СБП-подобный перевод в другую страну | Может вернуть дополнительные страновые поля и использовать другую расчётную валюту |
| `tcard2card` | Перевод на карту в другую страну | Помимо карты могут потребоваться страна и дополнительные реквизиты |
| `tsim` | Пополнение зарубежной SIM-карты | Номер и оператор должны соответствовать выбранной стране |
| `tnspk` | Трансграничная оплата по QR/НСПК | Используйте QR и ссылки из ответа API |

Префикс `t` отделяет трансграничный маршрут от локального. Не убирайте его и не
заменяйте тип локальным аналогом: это влияет на валюту, доступных исполнителей и
набор реквизитов.

## Международные банковские методы

| `payment.type` | Для чего нужен | Поля PayOut API |
| --- | --- | --- |
| `account_number_iban` | Перевод на IBAN | `customer.requisites.accountNumber` |
| `account_number_sepa` | Перевод SEPA | `accountNumber`, `cardholder`, `swiftBic` |
| `upi` | Перевод по UPI ID | UPI ID передаётся в `accountNumber` |
| `imps` | Индийский банковский перевод IMPS | `accountNumber`, IFSC в `swiftBic`, имя получателя в `cardholder` |
| `phone_pe` | Перевод PhonePe | `phone` и UPI ID в `accountNumber` |
| `phone_tm` | Специализированный перевод PhoneTM | Состав полей зависит от выбранного способа оплаты |
| `erip` | Платёж через ЕРИП | ERIP identifier в `accountNumber` |
| `transfer_via_id_card` | Перевод по идентификатору документа | `idCard` |

Названия полей API унифицированы, поэтому они могут отличаться от
пользовательского названия реквизита. Не переименовывайте ключи: например, IFSC
для `imps` всё равно передаётся как `swiftBic`.

## Ссылки, QR и e-commerce

| `payment.type` | Для чего нужен | Ограничения |
| --- | --- | --- |
| `payment_link` | Оплата по готовой URL | Используйте только `requisites.paymentLink` или `integration.link` из ответа. Не конструируйте URL самостоятельно. Текущий PayOut DTO не принимает входное поле `paymentLink` |
| `deeplink` | Переход в банковское приложение | Ссылка зависит от банка и устройства. Используйте ссылку из ответа, а `integration.link` сохраните как запасной вариант |
| `nspk` | QR/НСПК-сценарий | Ответ может содержать `paymentLink`, `rawQrCodeData`, `qrImageUrl` или платёжную строку. Не все поля приходят одновременно. Текущий PayOut DTO не принимает QR-manager-поля |
| `ecom` | Оплата картой с 3DS/OTP | Только по отдельному согласованию и с соблюдением PCI DSS. Карточные данные нельзя хранить; возможен статус `waiting_confirmation` |

Для согласованного H2H e-commerce объект `card` содержит обязательные поля:
`cardNumber`, `cardHolder`, `cardCvc`, `cardLifetimeMonth` и `cardLifetimeYear`.
Номер должен проходить проверку карты, CVC/CVV содержит `3–4` цифры, месяц —
`01–12`, год — две последние цифры и не может задавать истёкшую карту. Эти данные
передаются транзитно и не должны сохраняться или попадать в логи. В остальных
e-commerce режимах карту собирает платёжная страница; точный режим заранее
согласуйте с платформой.

## Ограничения API

### PayIn

- В [`POST /shop/orders`](/doc/api/payin/02-orders/#post-shoporders) объект
  `payment` можно не передавать для Redirect. Если он передан, `payment.type`
  обязателен.
- В [`POST /shop/orders/sync-requisites`](/doc/api/payin/02-orders/#post-shoporderssync-requisites)
  `payment.type` обязателен, потому что реквизиты ищутся сразу.
- В пошаговом H2H тип выбирается через
  [`PATCH /shop/orders/{id}`](/doc/api/payin/04-actions/#patch-shopordersid) только
  в `new`; затем запускается поиск реквизитов.
- `payment.bank` необязателен. Без него платформа подбирает доступный банк для
  указанного типа. Фактический банк всегда берите из ответа ордера.
- Поля плательщика берите из `customerFields`. Например, UTR в текущем PayIn DTO —
  ровно 12 цифр, последние цифры карты/телефона — ровно 4.

### PayOut

- `payment.type` обязателен и должен быть включён для магазина. Список можно
  проверить через методы PayOut.
- `payment.bank` формально необязателен. Для карты платформа сначала пытается
  определить банк по BIN; если банк не определён, используется настроенный
  запасной вариант. Если банк известен, лучше передать его явно.
- `phone`: от 7 до 16 символов; `cardInfo`: ровно 16 цифр;
  `cardholder`: не более 200 символов.
- `accountNumber`, `swiftBic`, `bic`, `idCard`, `beneficiaryName`,
  `expirationDate` и `taxId` принимаются как строки. Дополнительные ограничения
  выбранного способа оплаты берите из `fields[].pattern` и `fields[].maxLength`.
- Если метод требует поля, которого нет в
  [`customer.requisites`](/doc/api/payout/02-orders/#поля-customerrequisites-которые-принимает-public-payout-api),
  не используйте его без отдельного согласования.

## Ошибки выбора типа

| Ошибка | Причина | Что делать |
| --- | --- | --- |
| `P10000` | Код `payment.type` не найден | Проверить согласованный код или свою таблицу кодов |
| `P10001` | Тип оплаты не включён для магазина | Согласовать включение или выбрать другой разрешённый тип |
| `B10000` | Банк не найден или архивирован | Проверить согласованный код или свою таблицу либо не передавать банк, если это разрешено |
| `T10000` | Пара `payment.type + bank + currency` недоступна | Проверить согласованную пару или получить доступные сочетания через API |
| `O10001` | Тип не выбран перед поиском реквизитов | Передать `payment.type`, затем повторить допустимое действие |
| `O10005` | Для выбранного способа PayIn сейчас нет реквизитов | Предложить другой тип или банк |
| `O10011` | Провайдер отклонил карту в e-commerce | Показать отказ без автоматического повтора списания |
| `O10012` | Провайдер не принял код подтверждения e-commerce | Не считать платёж успешным; запросить новый код только по согласованному сценарию |
